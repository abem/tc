## 1. 概要

本文書は、文字起こし処理の変換履歴を永続化するデータストアの設計を定義する。
対象範囲は作業指示書4-1節の必須記載項目（データストア方式選定・テーブル定義・記録対象フィールド・
`core/` 統合ポイント・既存CLIワークフローへの影響）。データストア本体の実装、WebUIからの参照実装は
含まない。

## 2. データストア方式の選定

### 2-1. 比較（SQLite vs JSONL）

| 観点 | SQLite | JSONL |
|---|---|---|
| 依存追加要否 | 不要（`sqlite3` は Python標準ライブラリ） | 不要（標準 `json`） |
| 日付範囲・条件検索 | `WHERE processed_at BETWEEN ...` 等で直接実行可 | 全行読込＋アプリ側フィルタが必要 |
| キーワード検索（Phase3想定） | FTS5仮想テーブルで拡張可能（本設計はスキーマ上の余地のみ確保、実装はPhase3） | 全文走査が必須、件数増加で線形に劣化 |
| 同時書き込み安全性 | トランザクション・ロックが標準サポート | 追記のみなら安全だが、更新・削除は再書き込みが必要で競合リスクあり |
| サーバー構築要否 | 不要（ファイルベース、方針書2章の要件と一致） | 不要 |
| スキーマ変更容易性 | `ALTER TABLE` またはマイグレーションで対応 | スキーマレス（自由度は高いが型・必須項目の保証がアプリ側依存） |
| 複数履歴のMarkdown「まとめ出力」 | SQL集計・`ORDER BY` で抽出後にMarkdown整形 | 全行読込後にアプリ側で同等の整形が必要（性能差はデータ量次第） |

### 2-2. 選定理由

**SQLiteを採用する。** 理由:

1. 依存追加なし（`uv pip install` 不要。方針書3節「依存関係追加は段階的に」との整合性が高い）。
2. 方針書2章が要求する「履歴一覧・キーワード検索・日付絞り込み」を将来的にSQLで自然に実装できる
   （日付絞り込みは索引付きカラムで即座に対応、キーワード検索はPhase3でFTS5拡張の余地を残す）。
3. サーバー構築不要という方針書の制約（「サーバー構築不要な方式」）をJSONLと同等に満たす。
4. 同時書き込み（将来的にWebUIから複数タブ操作等）に対し、JSONLの再書き込み方式より安全。

JSONLはシンプルさで優位だが、検索性能・将来のFTS5拡張余地でSQLiteに劣るため不採用。

## 3. テーブル定義（DDL）

```sql
CREATE TABLE IF NOT EXISTS transcription_history (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    processed_at        TEXT    NOT NULL,   -- ISO8601 (例: 2026-08-06T12:34:56)
    source_type         TEXT    NOT NULL,   -- youtube / gdrive / local
    source_original     TEXT    NOT NULL,   -- 入力URLまたはローカルパス
    source_title        TEXT,               -- YouTubeタイトル等（取得できる場合のみ）
    model_name          TEXT    NOT NULL,   -- 例: Qwen/Qwen3-ASR-1.7B
    device               TEXT    NOT NULL,   -- cuda / cpu
    language             TEXT,               -- 検出言語コード（ja/en等、自動判定時は結果値）
    diarization_enabled  INTEGER NOT NULL DEFAULT 0,  -- 0/1
    include_timestamps   INTEGER NOT NULL DEFAULT 0,  -- 0/1（ForcedAligner使用有無）
    context_hints_used   INTEGER NOT NULL DEFAULT 0,  -- 0/1（context引数が空文字以外だったか）
    char_count            INTEGER NOT NULL,            -- 文字数統計（len(result.text)）
    duration_sec          REAL,                         -- 音声長（秒）
    processing_time_sec   REAL    NOT NULL,             -- 処理時間（秒）
    failed_chunks          INTEGER NOT NULL DEFAULT 0,   -- 分割処理での失敗チャンク数
    repeated_chunks        INTEGER NOT NULL DEFAULT 0,   -- 反復ループ検出チャンク数
    result_text            TEXT    NOT NULL,             -- 結果テキスト本体
    output_text_path       TEXT    NOT NULL,             -- output/ 内のファイルパス
    gdrive_url              TEXT,                          -- アップロード先URL（取得できた場合のみ）
    notes                    TEXT                           -- 備考（自由記述、既定NULL）
);

CREATE INDEX IF NOT EXISTS idx_history_processed_at ON transcription_history(processed_at);
CREATE INDEX IF NOT EXISTS idx_history_source_type ON transcription_history(source_type);
```

**設計メモ**:
- `result_text` にテキスト本体を保持し、かつ `output_text_path` にファイルパスも保持する
  （作業指示書4-1-3「結果テキスト本体・ファイルパス」の両方要求を満たす。冗長に見えるが、
  DBファイル単体でのまとめ出力生成・出力ファイル削除後の閲覧を両立するため意図的な冗長化）。
- Phase3の「キーワード検索」拡張時は `CREATE VIRTUAL TABLE transcription_history_fts USING fts5(result_text, content='transcription_history', content_rowid='id')` 相当のFTS5補助テーブルを追加する想定。本設計では列定義のみ確保し、FTS5テーブル自体の作成はPhase3スコープとする（作業指示書のスコープ外のため本設計に含めない）。
- DBファイル配置先は `output/history.db` を想定（`output/` 配下は既存構成で書き込み権限確認済みのディレクトリのため。config.yaml等での上書き可否は次節参照）。

## 4. 記録対象フィールド一覧（作業指示書4-1-3対応表）

| 作業指示書要求項目 | 対応カラム |
|---|---|
| 処理日時 | `processed_at` |
| 音源ソース | `source_type`, `source_original`, `source_title` |
| 使用モデル・デバイス・実行パラメータ | `model_name`, `device`, `language`, `diarization_enabled`, `include_timestamps`, `context_hints_used` |
| 文字数統計 | `char_count` |
| 処理時間 | `processing_time_sec`（付随して `duration_sec` も記録） |
| 結果テキスト本体・ファイルパス | `result_text`, `output_text_path` |

`failed_chunks` / `repeated_chunks` は作業指示書に明記された必須項目ではないが、既存の
`TranscriptionResult.metadata`（`core/transcription_interface.py` の `Qwen3ASREngine.transcribe()` が
格納、L657-663）に既に存在する値であり、履歴の品質判断材料として有用なため追加記録する
（コスト無し・任意追加のため越権ではないと判断。不要であれば計の指示でカラムを削除可能）。

## 5. `core/transcription_interface.py` / `core/cli_workflow.py` との統合ポイント

### 5-1. 現状のデータフロー（実装済みコードの事実確認）

```
transcribe.py: TranscribeLoader.process_with_progress()
  → core/cli_workflow.py: resolve_input_audio()        # 入力解決（音源DL等）
  → core/transcription_interface.py: UnifiedTranscriber.transcribe()  # ASR実行、TranscriptionResult返却
  → transcribe.py: TranscribeLoader.save_results(result, resolution, settings, folder_id)
      → output_file へテキスト書込み（build_output_file、core/cli_common.py）
      → core/cli_workflow.py: upload_transcription_result()   # GDriveアップロード（該当時のみ）
```

`UnifiedTranscriber.transcribe()`（`core/transcription_interface.py` L929-974）が返す
`TranscriptionResult` には `text` / `duration` / `processing_time` / `model_name` / `metadata`
（`failed_chunks` 等）が揃うが、**音源種別・元URL・出力ファイルパス・アップロードURLは
`transcribe.py` 側にしか存在しない**（`resolution` / `output_file` / `full_url` はいずれも
`save_results()` のローカル変数）。そのため記録に必要な全フィールドが揃うのは
`save_results()` の実行末尾時点である。

### 5-2. 統合設計方針

`UnifiedTranscriber.transcribe()`（`core/transcription_interface.py`）自体は変更しない。
理由: 同メソッドはASR実行に専念する既存の責務分離（`core/config.py`・`core/logging.py` 等と同様の
統一アーキテクチャ方針）を保っており、音源種別やファイル出力はこのクラスの関心事ではない。
ここに記録処理を混在させると、CLI以外の将来的な呼び出し元（WebUI等）でも同じ副作用が
発生してしまい、「WebUI・CLI双方から共用できるクラス抽象化」（方針書3節）の妨げになる。

代わりに、`core/cli_workflow.py` に既存の `upload_transcription_result()`（L88-122）と対称形の
新規関数を追加する設計とする（**関数シグネチャ・実装はPhase1実装フェーズで確定。本文書は
配置方針のみを設計対象とする**）:

```python
# core/cli_workflow.py（新規関数、設計方針のみ）
def record_transcription_history(
    *,
    result: TranscriptionResult,
    resolution: InputResolution,
    output_file: Path,
    settings: Dict[str, Any],
    gdrive_url: Optional[str] = None,
    db_path: Path = Path("output/history.db"),
) -> None:
    """変換履歴をSQLiteへ記録する。失敗しても例外を外へ伝播させない
    （既存ワークフローへの無影響要件、6節参照）。"""
```

**呼び出し元**: `transcribe.py` の `TranscribeLoader.save_results()`
（既存の GDrive アップロード try/except ブロックの直後、L236相当）。

**是正（査sa指摘反映）**: 当初案は「`full_url` がこの時点でスコープ内に揃っている」としていたが誤り。
`transcribe.py` L219-236実測: `full_url` は `if resolution.source_type in {"youtube", "gdrive"}:`
分岐の内側でのみ代入される。`resolution.source_type == "local"` の場合はこの分岐自体が
実行されないため `full_url` は未代入のままとなり、分岐外（record_transcription_history() 呼び出し時）
で参照すると `UnboundLocalError` になる。是正設計: `save_results()` 内で GDrive アップロードの
try ブロックに入る**前**（L218相当、`console.print(f"ローカル保存先: {output_file}")` の直後）に
`full_url: Optional[str] = None` を初期化し、`if resolution.source_type in {"youtube", "gdrive"}:`
分岐内で代入された場合のみ上書きされる構成にする。これにより `record_transcription_history()`
呼び出し時点で `full_url` は常に定義済み（アップロード対象外/失敗時は `None`）となり、
`gdrive_url` カラムへ `None` をそのまま渡せる。

## 6. 既存CLIワークフローへの影響評価

**無影響を設計目標とする（方針書3節「無影響であることが望ましい」に対応）。**

- 呼び出し位置は `save_results()` の最終ステップとし、テキスト保存・GDriveアップロードという
  既存の主要処理が完了した**後**に実行する（記録処理の失敗が主要処理をブロックしない配置）。
- 記録処理自体は既存の GDrive アップロード呼び出し（L219-236）と同一パターンの
  `try/except` で囲み、例外発生時は `console.print` で警告表示するのみとし、
  `process_with_progress()` 全体の例外伝播（L201-203、呼び出し元へ re-raise）には
  含めない設計とする。DB書き込み失敗が文字起こし処理そのものの失敗として扱われないようにする。
- `UnifiedTranscriber.transcribe()` のシグネチャ・戻り値構造は変更しないため、CLI以外の
  将来利用箇所（存在すれば）への影響もない。
