## 1. 予備調査結果（4-1節の設計決定）

### 1-1. 不具合2の是正方式

**採用方式**: 指示書の(a)(b)いずれとも異なる、より小さい変更で成立する第3案を採用したい
（指示書「他案の提示可」に基づく提案）。

**方式**: `resolve_input_audio()`（`core/cli_workflow.py` L31-90）は**既に** `output_dir: Path` を
必須引数として受け取り、YouTube/X経路ではそのまま `YouTubeClient(output_dir=str(output_dir))`
（同L54）へ渡している。`YouTubeClient.download_audio()`（`handlers/youtube.py` L111-115）が
決定的ファイル名(`{safe_title}_{video_id}.wav`)を生成するのは `self.output_dir` 配下であり、
**`output_dir` そのものをジョブ単位で一意にすれば、ファイル名生成ロジックや関数シグネチャに
一切手を入れずに衝突を回避できる**。

`webui.py` の `_enqueue_job()` から `_resolve_input()` へ渡す `output_dir` を、投入(enqueue)ごとに
`Path("output") / "queue_downloads" / <一意トークン>`（トークンは `uuid.uuid4().hex[:8]`）とする。
Google Driveアップロード・履歴DB等の既存コードは`output_dir`という上位ディレクトリ配下に何を
置くかを関知しないため、この変更は`webui.py`の呼び出し側だけで完結する。

**この方式の副作用・実装コスト**:
- **`core/cli_workflow.py` / `handlers/youtube.py` は無変更**（既存の`output_dir`引数をそのまま
  活用するため、シグネチャ追加・分岐追加が不要）。指示書(a)案（`download_audio()`へ新規
  `output_path`引数を渡す方式）より変更範囲が小さく、共有関数への影響がゼロという点で
  レビューコストも小さい。
- 指示書(b)案（重複検知・警告、または結果再利用）と比較すると、(b)は「同一URLを意図的に
  2回投入し設定を変えて比較したい」という正当な利用を妨げる可能性がある一方、本方式は
  そうした利用を制限しない。また(b)の「結果再利用」はどちらの`QueueItem`の完了時にファイルを
  削除すべきかという新たな状態管理（tc-ops #440で導入した「各QueueItemが`resolution`を専有する」
  という設計原則との整合性）が必要になり複雑化するため、採用しない。
- ダウンロード先が`output/queue_downloads/<token>/`という新規サブディレクトリ配下に変わるが、
  最終成果物の保存先(`build_output_file()`が書き込む`output/`直下のtranscriptionファイル)には
  影響しない（ダウンロード元の一時ファイル置き場のみの変更）。

### 1-2. CLI経路（`transcribe.py`）への影響確認

`transcribe.py` L152の呼び出し(`resolve_input_audio(input_info["source"], Path("output"), ...)`)は
**本是正で一切変更しない**（`webui.py`のみを変更するため）。CLI経路は指示書記載のとおり同時に
1ファイルのみ処理するため本バグの対象外であり、かつ`core/cli_workflow.py`/`handlers/youtube.py`
の関数シグネチャ・挙動を変更しないため、回帰の可能性はゼロと判断する（既存`uv run python -m
pytest -q`のCLI関連テストで裏付ける）。

### 1-3. Google Drive経路での同種衝突の有無

**衝突は起こり得ない（確認済み、対応不要）**。`handlers/gdrive.py`の`download()`（L408-415）は
`output_dir`引数を受け取らず、`tempfile.NamedTemporaryFile(delete=False, suffix='.mp3')`で
呼び出しごとに一意な一時ファイル名を生成している。同一ファイルを2回投入しても、`GDriveClient.
download()`は毎回異なる一時パスを返すため、tc-ops #440時点の設計（各`QueueItem`が`resolution`を
専有する）どおりに機能する。次チケットへの切り出しは不要と判断する。

### 1-4. 関連して発見した追加リスク（本チケットのスコープ外だが報告）

`webui.py`の`_resolve_input()`のローカルアップロード分岐（L127-140）も、同一ファイル名を
2回アップロードすると`output/uploads/<ファイル名>`が2件目のアップロード時に**上書き**される
（`_cleanup_temp_file()`はローカルアップロードを削除しないため、1件目のジョブが完了前に2件目の
書き込みで中身が差し替わるおそれがある）。指示書2節の不具合1・2はYouTube URL経路のみを対象と
記載されているため、本チケットのスコープには含めていない。上記1-1の方式を`_resolve_input()`に
適用する過程で、同じ仕組み（アップロード先も`output/queue_downloads/<token>/uploads/`のように
ジョブ単位ディレクトリ化）をローカルアップロード分岐にも**併せて適用することが実装コスト的には
ほぼ無償**（同じ関数・同じパラメータ追加で両分岐をカバーできる）なため、本チケットに含めるか
次チケットとするか、計のご判断を仰ぎたい。**含める場合は追加の機械検査項目は不要**（4-1節の
是正方式検証テストがローカル分岐にも同一パターンで拡張可能）。

## 2. 実装計画

### 2-1. 対象ファイル

- `webui.py`:
  - `_resolve_input(form_values, download_dir: Path)`: `download_dir`引数を追加。URL分岐は
    `resolve_input_audio(url, download_dir, ...)`へ渡す（既存の`output_dir`引数を活用）。
    （1-4節の追加リスクを含める場合）ローカルアップロード分岐も`download_dir / "uploads"`へ変更。
  - `_enqueue_job()`: 呼び出し直前に`download_dir = Path("output") / "queue_downloads" /
    uuid.uuid4().hex[:8]`を生成して`_resolve_input()`へ渡す。`_resolve_input()`呼び出しを
    `with st.spinner("入力を解決しています(ダウンロード等)...")`で包み、不具合1（UX）を解消する。
- `core/cli_workflow.py` / `handlers/youtube.py`: **無変更**（1-1節のとおり）。

### 2-2. 不具合1の改善方式

`st.spinner()`（Streamlit標準の「長時間処理中はスピナー表示」パターン）を`_enqueue_job()`内の
`_resolve_input()`呼び出しに適用する。「キューに追加」ボタン押下によるスクリプト再実行が
開始された時点でスピナーが即座に描画され、ダウンロード完了まで表示され続けるため、
クリック直後の無反応に見える問題を解消する。ボタン一時無効化等の追加実装は行わない
（`st.spinner`単体で要件を満たすため、最小差分を優先）。

### 2-3. 新規テスト方針（不具合2の再現テスト、完了条件のgrep対象）

`tests/test_webui_duplicate_url_download.py`（新設）:
- `handlers.youtube.YouTubeClient.download_audio()`をモックし、`resolve_input_audio()`（無変更の
  既存関数）へ**異なる`output_dir`**を2回渡した場合に、同一URL・同一動画情報（同じtitle/id、
  よって同一の決定的ファイル名）でも最終的な`local_audio_path`が衝突しないことを検証する
  （テスト名例: `test_duplicate_url_with_distinct_download_dirs_does_not_collide`。是正前の
  webui.py実装が2件とも同一`output_dir`を渡していたことに相当する対照ケース
  `test_duplicate_url_with_same_download_dir_collides_illustrating_the_bug`も併せて追加し、
  「同一dirなら衝突する／異なるdirなら衝突しない」の両方を機械的に裏付ける）。
- 上記テスト名はいずれも"duplicate"を含むため、指示書3節の
  `pytest --collect-only | grep -i "duplicate\|重複"`を満たす。
- `webui.py`自体はStreamlit依存のためこれまでどおり直接ユニットテスト対象に含めない
  （tc-ops #440時点と同じテスト境界を踏襲）。`_enqueue_job()`が実際に一意な`download_dir`を
  生成して`_resolve_input()`へ渡している配線自体は、完了報告時の実機操作ログ（同一URL2回投入
  →2件とも成功）で確認する。
