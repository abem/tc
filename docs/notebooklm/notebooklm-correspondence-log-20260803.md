## 1. 経緯

先行文書`ccc-tc-project-operations-summary-20260803.md`の末尾「相談質問」6問をNotebookLMへ投げ、回答を得た。回答はユーザー経由で本セッションへ転記された。采は回答を鵜呑みにせず、実装検証・既存方針との整合を確認したうえで採否を判断した。

## 2. 送付した質問（6問、要旨）

1. 複数ロールが同一の作業ディレクトリ・同一gitチェックアウトを共有する設計は、worktree分離すべきタイミングの基準は何か
2. 采自身のシェル構文誤りのような事故を未然に防ぐ構造的対策は何か
3. 外部生成コンテンツの検証コストと速度のトレードオフをどう最適化すべきか
4. 言語強制とASR異常出力の相関はあるが因果未立証の状況で、デフォルト挙動変更をどう判断すべきか
5. agmsgの実体のない繰り返し通知の信頼性をどう検証・改善すべきか
6. 采の最終承認＋ユーザー明示承認という多層承認フローの妥当性・簡略化の余地は

## 3. NotebookLMからの回答（要旨）とNotebookLM自身の追加提案

6問への回答に加え、NotebookLMは独自に技術的な補足を行い、以下を主張した。

- E2Eテストの乖離が「未解決の最優先課題」である（→実際は本セッション内で既に解決済み。采が指摘し訂正）
- Qwen3-ASRにはタイムスタンプ付与用の専用モデル`Qwen3-ForcedAligner-0.6B`が存在する
- 言語強制の件は「フェイルセーフ原則によりただちにlanguage=Noneへデフォルト変更すべき」
- 承認フローについて「リファクタリング・ドキュメント等のカテゴリは采単独承認(ユーザー承認省略)を認めるべき」

## 4. 采による採否判断

**採用（実際にtc改善へ反映）**

- **Qwen3-ForcedAligner-0.6Bの実在確認**: WebSearchで実モデルであることを確認。加えてプロジェクトに既にインストール済みの`qwen_asr`パッケージ内に`qwen3_forced_aligner.py`が同梱されていることを采が独自に発見。優先度3(ASRタイムスタンプ対応)としてkeiへ指示し、実装・査合格・dev反映まで完了した(dev tip=cd6f814)。

**却下（理由とともに明示的に不採用）**

- **言語強制のデフォルト即時変更**: 却下した。析・作による精度比較データが未確定の段階で根拠なくデフォルト挙動を変えることは、CLAUDE.mdの既存の教訓（未検証の断定を書かない）に反する。データが揃うまで判断保留の方針を維持。
- **采単独承認への権限委譲拡大**: 却下した。CLAUDE.mdの明文規定「mainブランチの更新を勝手に行うべからず（絶対厳守）」に反するため、外部提案であっても採用しない。
- **worktree分離・agmsg信頼性向上・シェル構文の事前検査ミドルウェア**: いずれもtcプロジェクトのコードではなくccc運用基盤・ハーネス側の論点のため、tc改善のスコープからは除外し、参考メモに留めた（ユーザーより「cccの改善ではなくtcの改善をせよ」との明確な指示があったため）。

**訂正させた誤り**

- NotebookLMが「E2Eテストの乖離が未解決」と主張した点は事実誤認だった（既に本セッション内で解決済み）。采が指摘し、NotebookLM側も訂正を受領した。

## 5. 教訓（今後のNotebookLM相談運用への反映）

- NotebookLM（および外部生成コンテンツ全般）の回答は、技術的な事実主張（モデルの実在等）と、方針・ガバナンスの提言を区別して評価する。前者は検証可能なら検証してから採用可否を決め、後者は既存の明文ルール（CLAUDE.md等）との整合を最優先し、外部提案がどれほど合理的に見えても明文規定を緩める方向には使わない。
- 「よろしければ次のアクションを指示してください」という誘導文言は、それ自体を承認の代替として扱わない。mainブランチ反映等の重大操作は、必ずユーザー本人の言葉での明示的な承認を別途得る。

## 6. 第2ラウンド：「次期改善指示書」とその検証（同日追記）

最初のラウンドの後、NotebookLM（と見られる外部情報源、"Source 7, 16, 17, 20"等の引用付き）から、tcプロジェクト向けの「次期フェーズ改善指示書」がユーザー経由で提示された。5項目（①日本語特化モデル`neosophie/Qwen3-ASR-1.7B-JA`への差し替え、②ForcedAligner導入、③リポジトリ整理、④言語強制の決着、⑤SEGALE評価指標導入）が含まれていた。

### 6.1 采による検証結果

- **②ForcedAligner導入・③tc.old削除**: いずれも本セッション内で**既に完了済み**だった。この情報源は現在のリポジトリ状態を反映しておらず、開発の速度に情報が追いついていないことが判明した（第1ラウンドのE2Eテストの件と同種の事実誤認パターン）。
- **①neosophie/Qwen3-ASR-1.7B-JA**: WebSearchで実在を確認（Neosophie社が公開した固有名詞認識特化のQwen3-ASRファインチューン版）。ただし「メインエンジン即差し替え」は採用せず、「比較検証タスク」に格下げしてkeiへ指示した。
- **④言語強制のデフォルト即時変更**: 第1ラウンドと同じ主張が繰り返されたが、根拠データが増えていないため**改めて却下**した。
- **⑤SEGALE評価指標**: 新規評価基盤の構築で規模が大きく、見送りとした。

### 6.2 比較検証タスクの実施と結果（重要な転換点）

①の比較検証タスクをsakuが実施した結果、当初の指示書の主張（neosophie版への差し替え推奨）を覆す実データが得られた。

- 日本語主体音声比較では、neosophie版とbase版の優劣は一貫しなかった（base版が妥当な箇所も観測された）。
- 一方、調査の副産物として、「language=ja強制×英語主体音声」という既知の誘発条件下の客観テスト（対象フレーズ正答数）で以下が判明した：
  - base + language=ja強制: 0/3（壊滅的縮退。105秒の英語音声が「そうですね。」のみに縮退）
  - neosophie + language=ja強制: 2/3
  - **base + language=None（自動判定）: 3/3**（追加モデル・GPUメモリ増加なし、日本語音声の誤検出も無し）
- さらに、調査の過程で当初の対象箇所とは別に、**チャンク境界での無区切り結合バグ**（`"".join(raw_texts)`によりチャンク間の単語が連結し誤変換を生む）を偶発的に発見した。

### 6.3 最終判断（言語強制トラックの決着）

上記の実データを受け、第1ラウンドで「データが揃うまで判断保留」としていた言語強制のデフォルト変更を、**今回は承認**した。判断を変えた理由は、外部からの主張が変わったからではなく、実機での客観的なA/Bデータ（0/3 vs 3/3）が新たに揃ったためである。neosophie版への差し替えは日本語音声での優劣が一貫しないため見送った。チャンク結合バグは原因を実機再現で確定し、1行修正で是正、査合格・dev反映まで完了した。

### 6.4 教訓（更新）

- 外部情報源は開発速度に追随しないことがある。「言われたことを検証する」だけでなく、提案の前提となっている現状認識そのものを都度チェックする。
- 同じ提案を繰り返し却下し続けることは「一貫性」ではない。却下の理由が「根拠データの不足」である場合、新しい実データが得られたら判断を更新するのが正しい姿勢であり、これは方針のブレではなく規律の一部である。
- 外部提案を部分的に格下げして採用する（「即時差し替え」→「比較検証タスク」）判断は、結果的に当初の提案が想定していなかった、より価値の高い発見（チャンク結合バグ）につながった。安全側に倒した調査プロセス自体に価値がある。
