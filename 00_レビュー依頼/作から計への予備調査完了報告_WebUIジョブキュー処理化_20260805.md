## 1. 予備調査結果（4-1節の設計決定）

### 1-1. キューのデータ構造と保持場所・採用方式

- **保持場所**: `st.session_state["job_queue"]`（キュー本体は `TranscriptionJobQueue` インスタンス1個。中身は `QueueItem` のリスト）。
- **次ジョブ起動の経路**: 新規スレッドや `queue.Queue` 経由の別機構は導入しない。既存の
  `_render_progress_and_result()`（`@st.fragment(run_every="1s")`）をそのまま流用・拡張し、
  **1秒毎のフラグメント再実行のタイミングで「現在処理中ジョブの完了検知→次のキュー項目の
  起動」を判定する**。
  - **根拠**: Streamlitは同一セッション内のスクリプト実行・フラグメント再実行を直列に処理し、
    同一セッションに対して並行実行しない（公式ドキュメント準拠の実行モデル）。既存コードも
    この前提で `st.session_state["job"]` を追加のロックなしに読み書きしている（`webui.py`
    L226, L238, L252-253等）。新方式もこの前提をそのまま踏襲すれば、キュー本体・状態遷移は
    追加のスレッド安全機構（Lock等）なしに安全に読み書きできる。
  - バックグラウンドスレッド側（`start_transcription_job()` の `_run()`）が触るのは
    `TranscriptionJob.progress_queue`（既に `queue.Queue` でスレッド安全）・`result`/`error`/`done`
    （単純代入、既存コードと同水準の安全性）のみで、キュー本体には触れない。役割分担を
    「スレッド側は自分のジョブの実行結果を書くだけ」「フラグメント側はキューの状態遷移を
    行うだけ」に限定することで、新規の排他制御を増やさずに済む。

### 1-2. ジョブ状態遷移

状態: `QUEUED`（待機中） → `PROCESSING`（処理中） → `DONE`（完了） / `FAILED`（失敗）

`QueueItem` が保持する情報（`core/webui_workflow.py` に新設）:

| フィールド | 内容 |
|---|---|
| `label` | UI表示用の投入内容の名称（URL文字列 or アップロードファイル名） |
| `resolution` | `InputResolution`（投入時に解決済み。1-4節で詳述） |
| `settings` | `job_settings` 相当のdict（モデル・device・言語・話者分離・タイムスタンプ・context） |
| `state` | `QUEUED` / `PROCESSING` / `DONE` / `FAILED` |
| `job` | `TranscriptionJob \| None`（`PROCESSING`遷移時にセット） |
| `log` | 進捗メッセージのリスト（`drain_progress()`の蓄積先、既存の`job_log`相当） |
| `submitted_at` / `started_at` / `finished_at` | 各状態遷移時刻 |
| `output_file` / `gdrive_url` | `_save_and_record()` 完了後の結果参照 |
| `error_message` | 失敗時のエラー内容 |

### 1-3. 既存の単一ジョブ処理経路との統合方針

新規関数への分離（既存関数の拡張ではなく置き換え）:

| 既存 | 変更後 |
|---|---|
| `_start_job()`（L136-166） | `_enqueue_job()` に置換。入力解決(`_resolve_input`)＋設定構築は現行踏襲、`start_transcription_job()` の呼び出しは行わず `QueueItem`（state=`QUEUED`）を生成し `job_queue` へ追加するのみ |
| （新設） | `_dispatch_next_job()`: `PROCESSING`状態の項目が無く、かつ`QUEUED`項目が存在する場合、先頭を取り出し `start_transcription_job()` を呼び `PROCESSING` へ遷移 |
| `_render_progress_and_result()`（L223-277） | `_render_queue_and_result()` に置換。フラグメント内で ①現在`PROCESSING`項目の進捗drain・完了検知・`_save_and_record()`呼び出し ②`_dispatch_next_job()`呼び出し ③待機件数／処理中対象／完了済み一覧のUI描画、を行う |
| `_save_and_record()`（L185-220） | **シグネチャ変更なし**。呼び出し元を「`QueueItem`単位」に変更するのみ（引数は当該itemの`resolution`/`settings`をそのまま渡す） |
| `main()`（L342-343） | ボタン文言を「実行」→「キューに追加」に変更し `_enqueue_job()` を呼ぶ |

`QueueItem`・状態遷移・キュー操作（`TranscriptionJobQueue.enqueue()` / `.dispatch_next()`）は
`core/webui_workflow.py` に実装する（Streamlit非依存、既存の `TranscriptionJob` 等と同様に
pytest単体テスト可能な形を維持するため。作業指示書3節の機械検査 `grep -rn "class.*Queue"
core/webui_workflow.py` にも整合）。`webui.py` 側は `st.session_state["job_queue"]` の保持と
UI描画のみを担当する。

### 1-4. 既存の一時ファイル削除処理（`_cleanup_temp_file()`）への影響と担保方法

**設計変更で構造的に解消する**: 現行は `st.session_state["job_resolution"]` という**単一の共有キー**
にジョブの`InputResolution`を保持しているため、新ジョブ投入時に上書きされる構造上のリスクが
本来ある（現行は同時に1ジョブしか存在しない前提のため顕在化していないだけ）。
新方式では `InputResolution` を各 `QueueItem` インスタンスの**専有フィールド**として保持し、
`_save_and_record()` は常に「今処理が完了した当該`QueueItem`が持つ`resolution`」のみを引数で
受け取って `_cleanup_temp_file()` に渡す。共有キーを廃止したことで、他ジョブの一時ファイルを
誤って参照・削除する経路が構造的に存在しなくなる（他item の `resolution` へアクセスする
コードパス自体を作らない）。

## 2. 実装計画

### 2-1. 対象ファイル

- `core/webui_workflow.py`: `QueueItem`（dataclass, 状態は`enum.Enum`）、`TranscriptionJobQueue`
  クラス（`enqueue()` / `dispatch_next()` / 完了処理ヘルパー）を追加。既存の`TranscriptionJob` /
  `start_transcription_job()` / `drain_progress()` / `segments_to_srt()` は変更しない。
- `webui.py`: `_start_job()`→`_enqueue_job()`置換、`_dispatch_next_job()`新設、
  `_render_progress_and_result()`→`_render_queue_and_result()`置換、`main()`のボタン呼び出し変更。
  `_resolve_input()` / `_save_and_record()` / `_cleanup_temp_file()` は変更しない。

### 2-2. UI（待ち件数・処理中対象・完了済み一覧、4-2-3対応）

`_render_queue_and_result()` 内で以下を描画:
- 待機件数（`QUEUED`件数のサマリ行）
- 処理中対象（現在`PROCESSING`項目の`label`＋進捗ログ末尾10行＋完了時の結果プレビュー、
  現行の結果表示部分を踏襲）
- 完了済み一覧（`DONE`/`FAILED`項目を`st.expander`等で新しい順に列挙、`label`・保存先／
  エラー内容を表示）

### 2-3. 新規ユニットテスト方針

`tests/test_core_webui_workflow_queue.py`（新設）で `core/webui_workflow.py` の
`QueueItem` / `TranscriptionJobQueue` を対象に、Streamlit非依存でテストする
（`start_transcription_job()`をモック注入し実際のスレッド起動は行わない想定）:

- 投入時は`QUEUED`で追加され、処理中ジョブがなければ即`dispatch_next()`で`PROCESSING`に遷移すること
- 処理中に追加投入しても既存の処理中ジョブを上書きしないこと（複数件`QUEUED`のまま蓄積）
- 現在ジョブが`done`のとき`dispatch_next()`で次の`QUEUED`項目が`PROCESSING`に遷移すること
- 現在ジョブが未完了のとき`dispatch_next()`を呼んでも状態が変化しないこと（逐次処理の担保）
- 失敗（`job.error`あり）時に`FAILED`へ遷移し、後続の`QUEUED`項目の処理開始を妨げないこと
- 各`QueueItem`が個別の`resolution`を保持し、他itemの`resolution`に影響しないこと

件数は現時点の見積もりで6件程度。実装時に境界値等が増えれば追加する。
