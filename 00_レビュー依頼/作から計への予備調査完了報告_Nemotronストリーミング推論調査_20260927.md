# 作から計への予備調査完了報告: Nemotronストリーミング推論調査

**報告日**: 2026-09-27
**報告者**: 作成ロール（作、saku）
**対象**: tc-ops #546（Nemotronストリーミング推論調査、予備）

## 実施概要

作業指示書（査読合格sa、commit 0d93da9）に基づき、隔離venv（`venv-nemotron/`）にインストール済みの`transformers==5.17.0`実ソースの読解と文献調査を行った。実際のストリーミング推論の実行・GPU使用・実装変更は行っていない。

## ストリーミングAPIの実在確認

### Transformers側（実ソース確認）

隔離venvの`transformers/models/nemotron_asr_streaming/`配下に、ストリーミング推論専用のクラス群が実在することを確認した。

- **`NemotronAsrStreamingGenerationMixin`**（`generation_nemotron_asr_streaming.py`）: `model_kwargs["encoder_past_key_values"]`・`model_kwargs["padding_cache"]`をチャンク間で保持・更新するロジックが実装されている（L61-63、L174-180実測）。`num_lookahead_tokens`は必須引数として扱われ、未指定だとエラーになる（L217-225実測）。
- **位置エンコーディングの上限回避の仕組み（重要な発見）**: `NemotronAsrStreamingEncoderRelPositionalEncoding.forward()`（`modeling_nemotron_asr_streaming.py` L364-372実測）は、`seq_length = 現在チャンクのフレーム数 + cached_frames`で`config.max_position_embeddings`（5000）を超えないかを検査する。**`cached_frames`はスライディングウィンドウ方式の左文脈キャッシュ**であり、実測で`config.sliding_window = 57`（実際のモデルconfig値、`AutoConfig.from_pretrained()`で実測）、すなわち`cached_frames`は常に高々`57-1=56`フレームに抑えられる（L931・L1046実測: "Sliding-window K/V cache"、`left_context = config.sliding_window - 1`）。これにより、**ストリーミングモードでは総音声長に関わらず`seq_length`が5000を大きく下回り続け、tc-ops #546で確認したオフラインバッチ推論のハード上限（音声長400秒相当）を原理的に回避できる**と判断できる。
- **モデルカード・公式ドキュメントの使用例**（transformers公式ドキュメント、予備調査#546で一次資料確認済み）: `processor.set_num_lookahead_tokens(N)`でチャンク長を選択（80/160/320/560/1120msの5段階）、音声を`input_features_generator()`で逐次供給しながら**1回の`model.generate()`呼び出し**（別スレッド、`TextIteratorStreamer`で結果を逐次取得）で完結する設計。ドキュメントには`[!NOTE] This is an experimental feature and the API is subject to change.`という明記がある（実装コストとリスクの節で後述）。

### NeMo側（文献調査）

NVIDIA公式モデルカード・関連情報（WebSearch実施）によれば、Cache-Aware FastConformer-RNNTアーキテクチャに基づくストリーミング推論として、(a) HuggingFace Transformersのチェックポイントを直接読み込みNVIDIA提供のストリーミング推論コードを使う経路、(b) NVIDIAがGPU対応コンテナ（gRPC/HTTP API、`build.nvidia.com/nvidia/nemotron-asr-streaming`等）として提供する経路、の2通りが存在することを確認した。(b)は現行のサブプロセスCLI設計とは大きく異なるサービス型アーキテクチャであり、本プロジェクトの既存パターン（隔離venv+単発サブプロセス）とは統合方式が根本的に異なる。

## 既存アーキテクチャとの統合方式

### 現状（実測）

`NemotronSubprocessEngine.transcribe()`（`core/nemotron_engine.py`）は、`_invoke_subprocess()`を常に1回だけ呼び出す設計（tc-ops #548是正で確立）。複数チャンクがある場合も、`scripts/nemotron_infer.py`内のループで各チャンクを**独立に**`model.generate()`する（チャンク間で`encoder_past_key_values`等の左文脈キャッシュを一切共有しない）。これがtc-ops #546で判明した「均等分割による文脈喪失」（#78、類似度0.897）の直接的な設計原因である。

### ストリーミング化した場合の統合方式案

重要な点として、ストリーミングAPIは**1本の音声に対し`model.generate()`を1回だけ呼ぶ**設計（内部でチャンク単位に逐次処理し、キャッシュを自動的に引き継ぐ）である。したがって:

1. **サブプロセス起動回数・通信方式は現状維持でよい**（`_invoke_subprocess()`を1回だけ呼ぶ設計は変える必要がない）。サブプロセス間通信をストリーム化する必要はない。
2. **`scripts/nemotron_infer.py`側の内部実装のみを置き換える**: 現状の「複数の独立した音声ファイルパスを受け取りループで`generate()`する」実装を、「1本の音声全体を読み込み、`processor.set_num_lookahead_tokens()`で選んだチャンク長で`input_features_generator()`を組み立て、`model.generate()`を1回呼ぶ」実装へ置き換える。
3. **`core/nemotron_engine.py`側の変更**: `_extract_chunk_wav()`・`compute_chunk_boundaries()`・`adjust_boundaries_to_silence()`（tc-ops #546是正で実装した350秒閾値の均等分割＋無音区間寄せ）による**ファイルレベルのチャンク分割自体が不要になる**可能性が高い。ストリーミングモードでは音声全体を単一のパスとしてサブプロセスへ渡し、チャンク分割は`nemotron_infer.py`内部（ミリ秒単位のmelフレーム粒度）で完結する。**チャンク粒度が根本的に異なる**（現行: 数百秒単位のファイル分割／ストリーミング: 80〜1120ミリ秒単位のメルフレーム分割）ため、既存の`CHUNK_THRESHOLD_SEC`・無音区間寄せロジックはそのままでは転用できない。

## 実装コストとリスク

### 学習コスト

`num_lookahead_tokens`とレイテンシのトレードオフ（5段階、80〜1120ms）、`processor`が提供する`num_samples_first_audio_chunk`等の内部プロパティに基づく正確なメルフレームスライシング、`TextIteratorStreamer`＋別スレッドという非同期パターンの理解が必要。予備調査（本報告書・過去のPhase1調査）で一次資料は把握済みのため、実装自体の学習コストは中程度と見積もる。

### 既存コードへの影響範囲

- `scripts/nemotron_infer.py`: ストリーミング用の新しい実行経路（`main()`内の分岐、またはストリーミング専用の別関数）が必要。既存の「複数ファイルパスをループ」実装は、ストリーミングを使わない短音声（閾値以下）向けに残す設計も検討可能。
- `core/nemotron_engine.py`: チャンク分割・無音区間寄せロジック（tc-ops #546是正で実装したばかり）が、ストリーミング採用時は不要になる可能性が高い。**直近の実装がすぐに置き換え対象になるリスク**がある点は計・采の判断材料として明記する。
- `scripts/compare_nemotron_baseline.py`（回帰ゲート）: ストリーミング実装後も基準比較の枠組みはそのまま使える見込み。

### リスク

1. **実験的API**: transformers公式ドキュメントに`"This is an experimental feature and the API is subject to change."`と明記されている。将来のtransformersバージョンアップでAPIが変更される可能性がある。
2. **性能未検証**: 短いチャンク長（例: 80ms）を選ぶほど多数回の内部処理が発生する（10分音声・80ms刻みで理論上7500回相当のチャンク処理）。1チャンクあたりのオーバーヘッド（Python/CUDAカーネル起動等）が蓄積し、実際の処理時間・RTFがオフラインバッチ推論より悪化する可能性があり、GPU実測での確認が必須。
3. **NeMo経路（コンテナ型）採用時の不確実性**: 予備調査（#546本体）で確認済みのとおり、`nemo_toolkit`の依存解決には無上限指定時のbacktrack事例（他プロジェクトの実例）があり、依存関係の不確実性は既知のリスクとして残る。またコンテナ型はgRPC/HTTPサーバーとして常駐させる設計であり、現行の単発サブプロセスCLI設計とは統合コストの性質が異なる（採用する場合はアーキテクチャレベルの再設計になる）。

## GPU実測計画案（実行はスコープ外、計画のみ）

ユーザー確認完了後、以下の実行を提案する:

1. **基準音声（#71と同一、328秒）でのストリーミング実装の妥当性確認**: `scripts/compare_nemotron_baseline.py`の枠組みを流用し、オフラインバッチ結果（基準、1007字、既に確認済み）とストリーミング実装での結果を比較する。328秒は現行閾値（350秒）以下でオフラインバッチでも分割不要なため、ストリーミング実装が同等の結果を再現できるかの妥当性確認に適する。
2. **10分（600秒）音声での長尺実測**: 現行のオフラインバッチ推論では確実に失敗する長さ（アーキテクチャ上限400秒を明確に超える）で、ストリーミング実装が実際に成功するかを確認する。測定項目: 総処理時間・RTF、ピークVRAM（`torch.cuda.max_memory_allocated()`/`max_memory_reserved()`、`scripts/nemotron_infer.py`に実装済みの計測をストリーミング経路にも追加）、文字数・内容の定性確認（`output/`配下は使わず、JSUT等の非本番音声を使用）。
3. **チャンク長（`num_lookahead_tokens`）ごとの性能比較**: 5段階（80/160/320/560/1120ms）のうち代表的な2〜3段階で、処理時間・RTFを比較し、精度と速度のトレードオフを確認する。
4. **既存2エンジン（Qwen3-ASR・Whisper）との回帰確認**: 同一環境でいずれかを実行し、Nemotronのストリーミング化による影響がないことを確認する。
