## 0. 計の一次確認で発見された不整合への対応（初版からの変更点）

初版報告後、計の一次確認で`output/history.db`に未削除のテストレコード5件（id 22-26、
`source_type=local`・`source_original=output/uploads/e2e_sample.wav`・`char_count=0`、
2026-08-05T15:30:12〜15:34:27）が残存していることが判明しました。

**原因**: `DEFAULT_HISTORY_DB_PATH`（`core/cli_workflow.py`）は`Path("output/history.db")`という
**プロセスのカレントディレクトリに対する固定パス**であり、**サーバーのポート番号には依存しない**
ため、1-2節表の#1-5（`systemd-run --user`一時ユニット、別ポート8502）での検証も、実際には
**本番と同一の`output/history.db`ファイル**へ書き込んでいました。「別ポートを使えば本番DBと
分離される」という誤った前提のまま検証・後片付けを行い、#1-5分（5件）を見落として#6-8分
（3件）のみ削除していました。

**是正**: id 22-26の5件（#1-5に対応することをタイムスタンプ・内容から確認済み）を事前バックアップ
の上で削除し、削除後の整合性（残存13件、対象外レコード無傷）を実測確認しました
（バックアップ: `backup/20260805_154643/history_backup_before_id22-26_delete.db`）。
以下、1-2節・副作用開示を実態（計8回試行、計8件のDBレコード生成）に訂正して再掲します。

### 1-3. 実際の過去の障害ログの発掘（最も重要な発見）

`journalctl --user -u tc-webui.service`で、tc-ops #441報告時点の実際の障害
（2026-08-05 15:11:23、サービス起動15:09:08から2分15秒後）の詳細ログを確認しました:

```
15:11:23,688 - UnifiedTranscriber - Starting transcription: ...
15:11:23,689 - perf.Qwen3ASREngine - Started: transcribe_...
15:11:23,734 - Qwen3ASREngine - ERROR - Transcription failed: No module named 'qwen_asr'
```

**"Started"から"failed"まで、わずか45ミリ秒でした。** 私が行った全ての試行（上記1-8、いずれも
成功）では、`qwen_asr`のimportに**4〜12秒**を要しています（診断ログ実測: `elapsed=4.62s`
「本番検証6」等）。この2桁〜3桁の時間差は、実際の障害が「通常のモジュール探索の末に見つからな
かった」という単純な失敗ではなく、**何らかの理由でPythonのimportシステムが極めて高速に
「見つからない」と判定した**可能性を示唆します（意図した実験条件を再現できていない可能性、
または`sys.path_importer_cache`等のimportシステム内部キャッシュに関連する可能性）。

この過去ログには`sys.path`等の詳細情報は含まれていません（診断ログ実装前の障害のため）。

## 2. 棄却した仮説（実測に基づく）

| 仮説 | 検証方法 | 結果 |
|---|---|---|
| ロケール差（`LANG`等） | `systemctl --user show-environment`と手動シェル`env`を比較 | **棄却**: 両者とも`LANG=C.UTF-8`で同一 |
| リソース制限（cgroup） | `systemctl --user show tc-webui.service`で`CPUQuota`/`MemoryMax`確認 | **棄却の可能性大**: いずれも無制限（infinity）。`LimitNOFILESoft=1024`は既定値で優先度低 |
| 環境変数キーの構成差 | `systemd-run --user`一時ユニットと本番プロセスの`/proc/<pid>/environ`をキー単位で`diff` | **棄却**: 18件のキーが完全一致（値のパターンも同一） |
| `VIRTUAL_ENV`/`PATH`のuv経由の子プロセスへの伝播不備 | 本番の実streamlitプロセス（uvの子）の`/proc/<pid>/environ`実測 | **棄却**: `VIRTUAL_ENV`・`.venv/bin`を含む`PATH`とも正しく子プロセスへ伝播済み |
| 「systemd経由の起動」自体が唯一の条件 | 本番`tc-webui.service`の実際の再起動を含む計8回の対照実験 | **棄却に近い**: systemd経由でも8回中0回再現。「systemd経由」だけでは不十分な条件と考えられる |
| 「サービス起動から実際の投入までの経過時間」（2分程度） | 本番再起動後、意図的に2分待機してから投入 | **棄却**: 経過時間を実障害と揃えても再現せず |

## 3. 残る候補（未検証・確定できなかった事項）

- **importシステム内部のキャッシュ異常**（1-3節の45ms手がかりから最も有力）: 具体的な検証
  （`sys.path_importer_cache`の内容を実際に記録する等）は今回実施できていません。次に実際の
  障害が発生した際、現在追加済みの診断ログ（`sys.path`全内容）に加え、
  `sys.path_importer_cache`の内容も記録できるよう、診断ログのさらなる拡充が有効と考えられます。
- **極めて低確率のレースコンディション**: 実際の障害は采の報告で「2回連続再現」とありますが、
  今回詳細ログで裏付けが取れたのは1回のみです。今回の8回の試行で再現しなかったことは、
  「再現しやすい条件を発見できなかった」ことを意味し、「原因が存在しない」ことの証明には
  なりません。
- **Streamlitのfile watcher（WSL対応ポーリング型）との競合**（采候補3）: 今回、明確な相関は
  確認できませんでしたが、積極的に棄却できる証拠も得られていません（未検証寄り）。
