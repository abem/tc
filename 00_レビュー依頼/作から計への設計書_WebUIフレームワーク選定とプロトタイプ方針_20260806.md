## 1. 概要

本文書は、WebUI構築（方針書Phase2「最小構成WebUI（URL入力→文字起こし→履歴表示）のプロトタイプ」）
のフレームワーク選定と画面構成方針を定義する。作業指示書4-2節の必須記載項目5点に対応する。
最終的な技術選定は計の裁定事項であるため、本文書の選定案は「推奨」として記載する。

## 2. フレームワーク比較と推奨案

### 2-1. 比較（Streamlit vs FastAPI+シンプルフロントエンド）

| 観点 | Streamlit | FastAPI+シンプルフロントエンド |
|---|---|---|
| 開発コスト | 低い（単一Pythonスクリプトでフロント/バック一体、UIコンポーネントが標準提供） | 高い（API設計＋フロントエンド実装＋両者の連携実装が別途必要） |
| 保守性 | 依存が少なく学習コストも低い。ただしスクリプト全体再実行モデルのため状態管理（`st.session_state`）の設計規律が必要 | 責務分離は明確（API/UIが独立）だが、フロントエンド技術スタックが保守対象に加わる |
| 5分チャンク処理の非同期表示への適合性 | デフォルトのスクリプト再実行モデルは長時間処理のブロッキングを招きやすい。`st.fragment`（部分再実行）または別スレッド実行＋`st.session_state`でのポーリング型進捗共有が必要（後述4節） | WebSocket/Server-Sent EventsまたはFastAPI `BackgroundTasks`をネイティブサポートしており、長時間ジョブの進捗配信に技術的には最も適合する |
| サーバー運用の複雑さ | `streamlit run` 単一コマンドで起動、ローカル利用に十分 | Uvicorn等のASGIサーバー＋フロントエンド配信の二重運用、ローカル利用にはオーバースペック |

### 2-2. 推奨案

**Streamlit を推奨する。**

理由: 方針書のPhase2スコープは「最小構成WebUI（URL入力→文字起こし→履歴表示）のプロトタイプ」であり、
機能範囲を絞ったプロトタイプ段階では開発コスト・運用の単純さが優先される。5分チャンク処理の
非同期表示という技術的弱点は、`st.fragment`（Streamlit 1.37以降で導入された部分再実行機能）または
バックグラウンドスレッド＋`st.session_state`ポーリングで実用上対応可能と判断する（4節で設計）。

FastAPIは非同期処理の適合度でStreamlitに勝るが、フロントエンド実装コストがプロトタイプ段階では
過大であり、Phase2の完了条件（最小構成での動作確認）に対して投資対効果が見合わない。

**計への確認事項**: Phase3（履歴検索・エクスポート機能、UIブラッシュアップ）でStreamlitの
UIカスタマイズ制約が問題になった場合、FastAPI移行を再検討する前提でよいか、方針として
計の判断を仰ぎたい（本設計はPhase2時点の推奨であり、Phase3時点の技術選定を拘束しない）。

## 3. 主要画面構成

作業指示書4-2-2の必須項目5点それぞれについて構成を定義する。

### 3-1. 入力フォーム
- YouTube/GDrive URL入力欄（テキスト入力、`core/utils.py: detect_input_type()` で種別自動判定）
- ローカルファイルアップロード欄（`st.file_uploader`、`UnifiedConfig.system.allowed_file_types`
  と一致する拡張子のみ許可。**是正（査sa指摘反映）**: 当初案は `config/config.yaml` に
  `system.allowed_file_types` キーが存在する前提で記載していたが誤り（`grep`実測: `config.yaml`に
  `system:` セクション自体が存在しない）。実体は `core/config.py` の
  `SystemConfig.allowed_file_types`（L163-165、Pythonデフォルト値
  `[".wav", ".mp3", ".mp4", ".m4a", ".flac", ".ogg"]`）であり、`config.yaml` 側からの
  オーバーライドは現状未対応。WebUI側でこの一覧をユーザーが変更できる必要が生じた場合は、
  `config.yaml` に `system.allowed_file_types` キーを新設しオーバーライド可能にする対応が
  別途必要になる（本設計のスコープ外、必要性が生じた時点で計に確認））
- 入力タイプ判定結果の表示（YouTube/Google Drive/ローカルファイルのいずれかをUI上に明示）

### 3-2. 設定パネル
- モデル選択（`config.yaml` の `whisper.language_models` に定義された候補から選択、
  または `Qwen/Qwen3-ASR-1.7B` を既定値としてプリセット表示）
- デバイス選択（auto/cuda/cpu、既定は `core/utils.py: resolve_device("auto")` の解決結果）
- 言語選択（ja/en/自動判定、既定は `config.yaml` の `whisper.language: null`＝自動判定を踏襲）
- 話者分離オン/オフ切替（`DiarizationConfig.enable_diarization` に対応）
- タイムスタンプ付与オン/オフ切替（`TranscriptionConfig.include_timestamps` に対応。
  オンにするとForcedAligner追加ロードでGPUメモリ約1.2GB増（`core/transcription_interface.py`
  L462-465のコメント参照）である旨をUI上に注記する）

### 3-3. リアルタイム進捗表示
- 現在の処理段階（音源解決中／文字起こし中／保存中）のステータス表示
- チャンク分割処理時（音声長 > `Qwen3ASREngine.CHUNK_THRESHOLD_SEC`＝300秒）は
  「チャンクN/M処理中」形式の進捗表示（4節の非同期方式で実現）

### 3-4. テキスト・SRTプレビュー
- 文字起こし結果テキストのプレビュー表示（`TranscriptionResult.text`）
- SRTプレビュー: **現状SRT出力ロジックはコードベースに存在しない**
  （`grep`実測: `srt`/`SRT` を含むPythonファイル0件）。`TranscriptionResult.segments`
  （`start`/`end`/`text` を保持）から生成可能だが、`include_timestamps=True`
  （ForcedAligner使用時）でなければ segment は音声全体を1区間とする単一セグメントとなり
  実用的なSRTにならない（`core/transcription_interface.py` L634-647）。
  設計方針: SRTプレビューは「タイムスタンプ付与オン」時のみ表示し、`segments`から
  `HH:MM:SS,mmm --> HH:MM:SS,mmm` 形式へ変換する軽量整形関数を新設する想定
  （新設対象・配置先はPhase2実装フェーズで確定。本設計は方式のみを提示）。
  タイムスタンプ付与オフ時は「SRT生成にはタイムスタンプ付与を有効にしてください」の
  ガイダンス表示に留める。

### 3-5. 履歴一覧画面
- Phase1で設計したSQLite `transcription_history` テーブルを一覧表示
  （`processed_at` 降順、`source_type`・`model_name`・`char_count`・`processing_time_sec` を列表示）
- 各行から結果テキストの詳細表示（`result_text`）・GDrive URLへのリンク（`gdrive_url` が
  非NULLの場合）
- 日付絞り込み（`processed_at` へのSQL `WHERE` 条件）は方針書2章の要求どおりPhase2で実装対象、
  キーワード検索はPhase3スコープ（DB設計書5節参照）のため本プロトタイプでは検索欄を
  UI上に配置しない（スコープ外の先行実装を避ける）。

## 4. `context_hints`（ヒント入力欄）の設計

`config/context_hints.txt.sample` に記載された実機検証済みの幻覚リスク
（チャンク冒頭が無音・不明瞭な場合、ヒント語彙自体が「実際に発話された内容」として
出力に混入する。`core/transcription_interface.py` は全チャンクに同一のcontext文字列を
渡す実装のため、長時間音声の各チャンク境界で毎回発生しうる）を踏まえ、以下の設計とする。

- WebUI上の「ヒント入力欄」は**デフォルト非表示**とする（`st.expander` 等で折りたたみ、
  明示的に開いた場合のみ入力可能にする）。
- ヒント入力欄を開いた場合、直下に固定の警告文を常時表示する:
  「⚠️ 音声の無音・不明瞭区間で、ここに入力した語句が実際には発話されていない内容として
  出力に混入することがあります（実機検証済みの既知リスク）。出力結果は必ず目視確認してください。」
- ヒント入力を1文字以上行った場合、実行ボタン押下前に確認ダイアログ
  （`st.checkbox`「上記リスクを理解した上でヒントを使用する」への同意必須）を挟む設計とする。
- 記録面: Phase1のDB設計（`context_hints_used` カラム）と連動し、ヒント使用有無を履歴に残す
  （事後のリスク調査を可能にするため）。

## 5. 5分チャンク分割処理の非同期・安定動作方式

`Qwen3ASREngine.CHUNK_THRESHOLD_SEC = 300`（`core/transcription_interface.py` L577）を超える
音声は自動的にチャンク分割される（`_transcribe_long_audio()`、L673-801）。この処理は
CPUバウンドではなくGPU推論のため、Streamlit本体スレッドをブロックする長時間処理になる。

**設計方針**:
1. `UnifiedTranscriber.transcribe()` の呼び出しを Python標準の `threading.Thread` で
   別スレッド実行する。
2. 進捗共有は `queue.Queue`（スレッドセーフ）を介し、ワーカースレッドが
   `progress_callback`（`UnifiedTranscriber.transcribe()` は既に `progress_callback`
   引数をサポート済み、`core/transcription_interface.py` L932）経由でキューへ進捗文字列を
   `put()`、メインスレッド側は `st.session_state` に反映する。
3. UI側の自動更新には `st.fragment(run_every="1s")`（Streamlit 1.37+の部分再実行機能）を
   採用し、進捗表示部分のみを1秒間隔で再描画する。これにより画面全体の再実行
   （Streamlitのデフォルト動作）によるチラつき・状態喪失を避ける。
4. `_transcribe_long_audio()` 自体（チャンク単位の失敗プレースホルダ挿入・反復ループ検出
   と1回のみ再試行、L708-801）は既存ロジックを変更しない。WebUI側はこの既存の
   耐障害設計をそのまま利用し、`TranscriptionResult.metadata` の `failed_chunks`／
   `repeated_chunks` を進捗表示・完了時の警告表示に反映する（`transcribe.py`
   L184-192の既存CLI表示ロジックと同等の扱いをWebUI側でも踏襲）。

**代替案として検討し不採用としたもの**: `asyncio` ベースの非同期化。
理由: `UnifiedTranscriber.transcribe()` および内部のtorch推論呼び出しは同期APIであり、
`asyncio`化には `run_in_executor` 相当のスレッドプール委譲が結局必要になるため、
素直な `threading.Thread` 方式に対する利点が薄いと判断した。

## 6. `core/` ロジックのクラス抽象化方針

方針書3節「`core/transcription_interface.py` / `core/cli_workflow.py` のロジックをクラス抽象化し、
CLI・WebUI双方から共用できる構成とすること」への対応方針。

**現状評価（実測）**: `core/transcription_interface.py` の `UnifiedTranscriber` は既に
CLI固有の関心事（引数パース・Rich表示・GDriveアップロード）を含まない、ASR実行に専念した
クラスとして設計済みである。`core/cli_workflow.py` の `resolve_input_audio()` /
`upload_transcription_result()` も同様に、`console.print` 等のCLI表示処理を呼び出し元
（`transcribe.py`）に残し、`on_status` コールバック経由で通知する疎結合な設計になっている
（`core/cli_workflow.py` L37-39）。

**結論**: `UnifiedTranscriber` 自体の構造変更は不要であり、CLI・WebUI双方から直接
`import` して共用可能である。追加抽象化が必要なのは、5節で設計した「非同期実行＋進捗共有」の
部分のみであり、これは新規のラッパー層（例: `core/async_workflow.py` 相当、命名・配置は
実装フェーズで確定）として `core/cli_workflow.py` と同階層に追加する設計とする。
既存の `resolve_input_audio()` / `UnifiedTranscriber.transcribe()` /
`upload_transcription_result()` はいずれも変更せず、ラッパー層から呼び出す構成とすることで、
既存CLIワークフロー（`transcribe.py`）への影響をゼロに保つ。
