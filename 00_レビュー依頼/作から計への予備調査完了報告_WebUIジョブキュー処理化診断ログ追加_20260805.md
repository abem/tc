## 1. 予備調査結果

### 1-1. 診断ログの追加箇所・実装方針（4-1節対応）

指示書1〜5の各ポイントについて、`core.logging.get_logger(__name__)`（既存統一ロガー方式）で
以下を追加する。

**`webui.py`**（`logger = get_logger(__name__)` を追加）:
1. `_enqueue_job()`冒頭: `token = uuid.uuid4().hex[:8]` を**現状のL176から関数の最初の行へ
   繰り上げ**、生成直後に `logger.info("enqueue試行開始 token=%s ...", token)` を出力する
   （指示書の「生成タイミングをログ出力より前に早める必要があれば報告」に該当。現状は
   `download_dir`生成がL176で関数冒頭に近いため、繰り上げ自体は数行の移動のみで済む）。
2. `_resolve_input()`呼び出し直前に`logger.info("_resolve_input開始 token=%s", token)`、
   直後（`try/finally`不要、例外発生時は指示書の主目的どおりログが出ないこと自体が証跡になる
   ため意図的にfinallyにしない）に`logger.info("_resolve_input完了 token=%s elapsed=%.2fs", ...)`
   を出力する。
3. `_get_queue().enqueue(...)`の戻り値（既存で`QueueItem`を返す）を受け取り、
   `logger.info("enqueue完了 token=%s item_id=%s", token, item.item_id)`を出力する。

**`core/webui_workflow.py`**（`logger = get_logger(__name__)` を追加）:
4. `TranscriptionJobQueue.enqueue()`: item_id採番直後に
   `logger.info("状態遷移 item_id=%s (新規)→QUEUED label=%s", ...)`（webui.py側のログと
   ほぼ同時刻に出るため、token↔item_idの対応関係を突き合わせる材料になる）。
5. `dispatch_next()`: 呼び出しの都度、`logger.debug("dispatch_next呼び出し current_item_id=%s
   queued_count=%d", ...)`。実際に起動した場合は`PROCESSING`遷移時に
   `logger.info("状態遷移 item_id=%s QUEUED→PROCESSING label=%s", ...)`。
6. `mark_done()` / `mark_failed()`: 遷移直前に
   `logger.info("状態遷移 item_id=%s PROCESSING→DONE/FAILED ...", ...)`。

いずれも`item_id`（またはenqueue前は`token`）を含むため、指示書の要件（「①のトークンで
ダウンロード開始から③のenqueue完了まで一意に追跡できる」）を満たす。機械検査
`grep -n "logger" core/webui_workflow.py webui.py | grep -i "enqueue\|dispatch\|item_id"`は
上記6箇所いずれも該当する。

### 1-2. 原因についての事前調査（コード根拠、実機再現前の仮説精査）

**Streamlit公式実装のソースコードを確認した**（本プロジェクトの`.venv`にインストール済みの
streamlit 1.60.0、`streamlit/runtime/scriptrunner/script_runner.py` L456-505
`_maybe_handle_execution_control_request()`）。同関数のdocstring原文:

> "This function is called every time the app script enqueues a ForwardMsg, which means
> that most `st.foo` commands - which generally involve sending a ForwardMsg to the
> frontend - act as implicit yield points in the script's execution."

実装（L501-503）:
```python
if request.type == ScriptRequestType.RERUN:
    raise RerunException(request.rerun_data)
```
`RerunException`は`BaseException`を継承する（`exceptions.py`のコメント: 「ユーザーコードの
try/exceptに捕まらないように意図的にBaseException継承」）。

**このコードから読み取れる事実**: `_enqueue_job()`が`_resolve_input()`を呼び出す間、
`resolve_input_audio()`（YouTube/X経路、`core/cli_workflow.py` L47）内部で
`on_status=st.write`（`webui.py`L130で配線済み）が呼ばれるたびに、Streamlit内部で
「保留中のRERUNリクエストの有無」がチェックされる。もし2件目のボタンクリックによる
RERUNリクエストが既にこの時点で届いていれば、`RerunException`（`except Exception`では
捕捉不可）が**その場で**送出され、`_enqueue_job()`の残りの処理（`_get_queue().enqueue()`を
含む）は一切実行されないままスクリプト全体が中断・再実行される。

**これは原理の確認であり、原因の確定ではない**（指示書の要求どおり、ログによる実機裏付けが
必須）。1-1節の診断ログを実装したうえで4-2節の実機再現を行い、実際にこの経路を通っている
ことをログの記載事実（「enqueue試行開始」は出るが「_resolve_input完了」「enqueue完了」が
出ない、というログの欠落パターン）から確認する。**この事前調査結果を前提に是正実装を
先取りすることはしない**（指示書の禁止事項どおり、本チケットは原因確定までに留める）。

### 1-3. テストの仕組みの設計方針（4-3節対応）

**既存の`streamlit.testing.v1.AppTest`（Streamlit公式テストフレームワーク）は不採用**と判断する。
理由: `AppTest.run()`は1回のスクリプト実行を完全に同期・完結させる実行モデルであり、
「ダウンロード処理がブロッキングで実行されている最中に、別のイベント（2件目クリック）が
割り込んで中断する」という**実行中の競合状態そのもの**を再現できない（`AppTest`はスクリプト
再実行後の状態差分を検証する用途であり、実行途中の割り込みは表現できない）。

**2層構成を提案する**:

**(A) 単体テスト（pytest、新規依存なし、`uv run python -m pytest -q`に含める）**:
`webui.py`の実際の`_enqueue_job()`を対象に、`_resolve_input`をモンキーパッチし、
`on_status`コールバック相当の呼び出しタイミングで`BaseException`派生の例外（実際の
`RerunException`と同じ性質＝`except Exception`で捕捉不可、を再現する軽量ダミー例外。
本物の`RerunException`は`RerunData`という内部専用オブジェクトを要求し、Streamlit内部APIへの
依存を増やすため、性質の再現に必要な最小限（`BaseException`継承）のみをテスト用に用意する）
を送出させ、`_get_queue().items`（またはテスト用に注入したキュー）が変化していないこと
（＝1件目が消失する現象そのものを、実際の関数`_enqueue_job()`に対して機械的に再現・固定化する）
を検証する。**これは「原因確定後に是正実装すると挙動が変わる」ことを前提にした特性テスト
（characterization test）であり、次チケット（是正実装）の際にこのテストのアサーションを
反転（1件目が生き残ることを検証）させる想定であることをテスト内コメントに明記する。**

**(B) 実機Playwright再現スクリプト（リポジトリに再利用可能な形でコミット、`pytest -q`
バッテリーには含めない）**: 4-2節の実機再現手順をアドホックな使い捨てスクリプトで終わらせず、
`scripts/repro_webui_concurrent_enqueue.py`として再利用可能な形でコミットする。実行には
システムにインストール済みのplaywright（本プロジェクトの`pyproject.toml`には追加しない、
既存の`scripts/e2e_local.sh`と同様「手動実行可能な検証ツール」という位置づけ）を用いる。
このスクリプトは今後、是正実装後の検証や、査(sa)の実機グラウンディング検査（6節申し送り事項の
「同時操作シナリオ」）にもそのまま再利用できる。

**ユーザー指摘「テストの仕組みちゃんと作って」への対応方針**: (A)は自動化された機械検査として
`pytest -q`に組み込み継続的に実行される。(B)は実機での「本当に動いているか」の確認手段として
再利用可能な形で保存する。両方を備えることで、単体テストレベルの機械的固定化と、実機での
target検証の両方を「仕組み」として提供する。
