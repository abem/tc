## 2. 背景と目的

`tc-webui.service`（systemd --user）を起動/再起動した直後、WebUI上で最初に投入した文字起こし
ジョブが必ず以下のエラーで失敗する（ユーザー実機で2026-08-05に2回連続再現、tc-ops #441）:

```
Qwen3ASREngine - ERROR - Transcription failed: No module named 'qwen_asr'
```

`core/transcription_interface.py`の`Qwen3ASREngine._load_model()`（L418-450）内、
`from qwen_asr import Qwen3ASRModel`（L428）が失敗の直接原因。

**采による切り分け結果（tc-ops #441記載、既知の事実として扱う）**:
1. `.venv/lib/python3.12/site-packages/qwen_asr/`は常に存在し正常（壊れたインストールではない）
2. `pyproject.toml`/`uv.lock`は直近変更なし（依存関係の再解決は発生していない）
3. `uv run python -c "..."`で実アプリと同じコードパスを直接シミュレートしたが**再現しなかった**
   （device='cpu'/'cuda'両方で確認済み）
4. systemdプロセスの環境変数（`/proc/<pid>/environ`）は`VIRTUAL_ENV`・`PATH`とも一見正常

**再現条件の要点**: systemd（`systemctl --user start/restart tc-webui.service`）経由で起動した
直後の最初の1回のみ確実に再現する。同一プロセス内の2回目以降は必ず成功する。
`uv run python`での直接シミュレーションでは再現しない。

**本文書の対象範囲**: 原因調査までとする。**是正実装は原因確定後、別途作業指示書を発行する**
（tc-ops #440是正2〜3で確立した「原因確定→計承認→是正実装」の順序を踏襲）。

## 4. 成果物の仕様・要件

### 4-1. 予備調査で検討すること（調査方針を計へ報告、承認を得てから調査実施）

**采が示した候補（いずれも仮説、調査で確認・棄却すること）**:
- `systemd-run --user`等でsystemdに近い起動条件を再現し、実際に`from qwen_asr import ...`が
  初回のみ失敗する条件を特定する
- systemdユーザーセッションの環境変数がインタラクティブシェルと異なる点（ロケール・ulimit・
  cgroup等）の影響有無
- Streamlitのポーリング型ファイル監視（WSL対応）が起動直後の何らかのタイミングと競合していないか

**saku独自の追加調査観点があれば提案してよい**（例: `qwen_asr`パッケージの`__init__.py`や
依存ライブラリ側の遅延初期化・C拡張のロード順序、Pythonの`sys.path`確定タイミングと
Streamlitのスクリプト実行開始タイミングの関係、等）。

**検討観点**（予備調査で報告すること）:
- 各候補をどう検証するか（`systemd-run --user`での再現実験の具体的な設計、ログ収集方法）
- 本番`tc-webui.service`を止めずに検証する方法（ユーザーが実際に使用中の可能性があるため、
  検証用の別サービスまたは`systemd-run --user`の一時的な単発実行を用いること。本番サービスの
  再起動を伴う検証が必要な場合は、事前に計へ確認すること）
