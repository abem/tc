## 2. 背景と目的

tc-ops #440（WebUIジョブキュー処理化、dev tip=869d676で反映済み）について、采が受入検証（実機）を
実施した結果、main反映前に2件の不具合が確認された。main反映は保留を継続し、本作業指示書により是正する。

**不具合1（UX、実害は小）**: `_enqueue_job()`（`webui.py` L165-181）が `_resolve_input()` 経由で
YouTube/Google Driveのダウンロードを同期実行する（実測7-12秒）。「キューに追加」クリックからこの間、
UI上に状態変化が無く、クリックが効いていないように見える。

**不具合2（実害あり）**: 同一URLを2回投入すると、1件目は成功するが2件目が
「Audio file not found」で失敗する。原因: `handlers/youtube.py` の `download_audio()`
（L111-115）が `output_path` 未指定時に `{safe_title}_{video_id}.wav` という完全に決定的な
出力パスを生成するため、同一URLに由来する2つの `QueueItem` が同一ファイルパスを共有する。
1件目完了時の `_cleanup_temp_file()` がそのファイルを削除し、後続の2件目が既に消失した
ファイルを参照して失敗する。`QueueItem` が導入時に意図した「クリーンアップが他項目へ波及しない」
という構造的保証（`core/webui_workflow.py`、`resolution` の項目専有）は、ディスク上のファイルパス
衝突までは実際には防げておらず、成立していない。

## 4. 成果物の仕様・要件

### 4-1. 予備調査で技術検討・決定すること（実装着手前に計へ報告、承認を得る）

**不具合2の是正方式**（いずれか、または他案の提示可。決定は計へ報告し承認を得る）:
- (a) **ダウンロード出力パスのジョブ単位一意化**: `webui.py` から `resolve_input_audio()` /
  `download_audio()` へ、`QueueItem` ごとに一意な出力パス（例: uuid4やタイムスタンプ＋連番の
  サフィックス）を渡せるようにする。**`resolve_input_audio()`（`core/cli_workflow.py` L31-90）は
  `transcribe.py`（L152、CLI経路）からも呼ばれる共有関数のため、変更時はCLI側の既存呼び出し
  （出力パス未指定時の挙動）に影響がないことを確認すること。**
- (b) **重複投入の検知・再利用**: 同一URLが既にキュー内（待機中または処理中）に存在する場合、
  UI上で警告する、または既存のダウンロード結果を再利用する方式。

**検討観点**（予備調査で報告すること）:
- (a)(b)それぞれの副作用と実装コスト
- `tc` / `transcribe.py`（CLI経路）への影響有無（CLI経路は同時に1ファイルのみ処理するため
  本バグの対象外だが、共有関数を変更する場合は回帰が無いことを確認すること）
- Google Drive経路（`handlers/gdrive.py` の `download()`）で同種のファイルパス衝突が
  起こり得るか確認し、起こり得る場合は本チケットで扱うか次チケットへ切り出すか計へ提案すること

### 4-2. 不具合1（UXフィードバック不足）の改善

「キューに追加」クリック直後、ダウンロード処理中であることをUI上で示す（例: スピナー表示・
ボタン一時無効化・「追加処理中」メッセージ等、具体的な実装方式はsaku判断で決定してよい）。

### 4-3. 対象外（スコープ外、実施しないこと）

- 複数ジョブの並列実行（tc-ops #440時点の方針を継続、対象外）
- キューの永続化
