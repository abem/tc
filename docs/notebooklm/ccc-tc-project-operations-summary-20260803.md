## 1. 前提（対象システム・登場人物の最小説明）

**tc（transcribe_audio）**: 個人利用の音声・動画文字起こしツール。Qwen3-ASR / Whisperベースのエンジンを切り替え可能で、YouTube・X（旧Twitter）・Google Driveから音声を取得し、文字起こし結果をGoogle Driveへ保存する。Pythonリポジトリ、GitHub上でホスト。

**ccc（Claude-Code-Communication）**: 複数のClaude Codeセッションを役割分担させ、階層的に協働させるための運用フレームワーク。5つのロールがあり、それぞれ別セッションのClaude Codeが担当する。

- **采（sai）**: 統括ロール。方針指示・最終決裁を担う。実装やGit操作は行わない。特にmainブランチへの反映は、必ず人間（プロジェクトオーナー）の明示的な承認を得てから計へGOを出す運用としている。
- **計（kei）**: リーダーロール。作業指示書の発行、進捗管理、Git操作（ブランチ作成・マージ・push）を専任する。査の合格判定を受けて最終承認しdevへ反映する。
- **作（saku）**: 作成ロール。実装・ドキュメント作成・スクリプト作成を担う。
- **査（sa）**: 検査ロール。実装内容を独立に再現検証し、合格／不合格の二値判定を下す。
- **析（seki）**: 分析ロール。データ分析・横断調査・監視を担う。実装は行わない。

ロール間の通信は`agmsg`という自作のエージェント間メッセージング基盤（SQLiteベース、各セッションがMonitorでリアルタイム購読）を使う。**重要な構造的特徴**: 5ロールは別々のセッションだが、**同一の作業ディレクトリ・同一のgitチェックアウトを共有**しており、git worktreeによる物理分離はしていない。そのため「1ブランチずつ順次進める」という運用上の取り決めで衝突を回避している。

標準的な作業フロー: `feature branchを作成(main起点) → 作が実装 → 査が独立検証し合否判定 → 計が最終承認しdevへマージ・push → 采がユーザーの明示承認を得てGOを出す → 計がdevをmainへマージ・push`。

## 2. 主題・背景

本ファイルが対象とするのは、tcプロジェクトでccc体制を新規に立ち上げてから約4〜5時間の1セッションで実際に何が起き、どう運用されたかの記録である。ccc体制自体はテンプレートとして他案件から持ち込まれたものであり、tcプロジェクトでの実運用はこのセッションが最初のまとまった実績となる。

## 3. 現状／経緯／実施したこと

**① ccc体制の立ち上げ**: 采が`/agmsg actas sai`でロールを確立し、ロール定義文書（3ファイル）を読了。計から「計・作・査・析の4名がロール定義読了」という集約報告を受けて立ち上げ完了とした。

**② ASR反復ループのバグ修正**: ユーザーから「文字起こし後半で同じ文が何十回も反復し読み取り不能になる」との報告。采が実出力ファイルを直接確認して事象を確定させ、計へ方針指示。原因は「チャンク単位のASR推論が反復ループに陥ると、無エラーのままチャンク全体が意味的に破壊される」こと。作が(a)generation_configへの反復抑制パラメータ設定、(b)反復検出ヒューリスティックによる1回リトライ、(c)チャンク単位ログ、を実装。査が独自の再現検証（pytest全数実行・新規テスト個別実行・実障害テキストへの直接呼び出し）を行い合格判定。ユーザーの明示承認を得てmain反映まで完了した。

途中、対象音声ファイルが自動削除済みで実音声E2E再現が不可能という制約が判明し、フィクスチャテストを主・合成音声補助検証を副とする完了条件へ采が承認のうえ変更した。

**③ 言語強制の副次調査（未解決・継続中）**: バグ修正の過程で、`config.yaml`の`language: ja`が全音声に強制適用されており、英語主体の音声に対しても日本語を強制していることが判明。析が過去出力95件を横断調査し、同型の異常（反復ループまたは日本語混入）が計4件で見つかり、いずれも「英語ソース音声×language=ja強制」という条件を共有していた。ただし対象音声の大半が削除済みで、直接の音声照合による因果立証はできていない。采は「デフォルト挙動の変更は時期尚早」と判断し、作による`language=None`（自動判定）との精度比較が揃うまで判断を保留する方針を取った。

**④ 外部生成の改善指示書の検証と一部実行**: GitHubへ公開した本リポジトリを基に外部で生成されたと見られる「改善指示書」をユーザーが提示。采はこれを鵜呑みにせず、各項目を実装コードと照合してから計へ指示した。結果、2件の誤りを検出できた：
  - 「デッドコードだから削除すべき」という指摘に対し、実際にはコード内に「意図的に残している」という設計コメントが既にあった。
  - 「未使用ファイルだから削除可能」という指摘に対し、作が実装前に裏取りしたところ、実際には複数の公式ドキュメントが現行の正式なCLIエントリポイントとして案内している生きたコードだと判明し、削除を未然に防いだ。

  この過程で別のドキュメント記述の乖離（既に削除済みのファイルを「削除禁止の重要ファイル」と誤記載）も偶発的に発見され、次サイクルの是正候補として記録した。

**⑤ リポジトリの公開設定変更**: ユーザーからの「private→publicにしてよいか検討して」との依頼を受け、采が独立にセキュリティレビューを実施。全gitブランチ・全コミット履歴を横断してAPIキー・秘密鍵・認証情報のパターンを検索したが該当なし。ただし設定ファイルの履歴に実在のGoogle Drive個人ファイルへのリンクが7件残存していることを発見。Google Drive APIで実機確認したところ、7件とも非公開設定（リンク共有無効）であり、実際のアクセスリスクは低いと判断。ユーザーが公開を決定し、GitHub API経由で公開設定への変更を確認した。

**⑥ 采自身の誤操作とその是正**: 采がagmsgでメッセージを送信する際、メッセージ本文中のバッククォート（`` ` ``）記法がbashのコマンド置換として解釈され、意図せず実際の文字起こしジョブが実行されてしまう事故が発生した。ログを確認しGoogle Driveへの誤アップロードは発生していないことを確認したうえで、ユーザーへ即座に透明性をもって報告し、メッセージを安全な形式で再送した。

## 4. 構造的な論点・課題

- **作業ディレクトリの共有**: 5ロールが同一のgitチェックアウトを共有しており、worktree分離をしていない。計は「1ブランチずつ順次進める」という運用ルールで対処しているが、これは規模が大きくなった場合にスケールしない可能性がある。

- **AIエージェント自身の操作ミス**: 采（本セッション）自身がシェル構文の扱いを誤り、意図しないコマンド実行を引き起こした。実害は限定的だったが、多エージェント運用において「エージェントの発信内容がそのまま実行コンテキストに影響しうる」構造的リスクが顕在化した。

- **未解明のまま繰り返す通知**: agmsgの「未反応N件あります」という通知が、実際には受信箱・履歴とも変化がない状態で数十回にわたり同一内容のまま繰り返し発火する現象があった。原因は特定できていない。実害はなかったが、多エージェント間メッセージング基盤の信頼性検証としては未解決の論点。

- **相関はあるが因果が立証できない不具合**: 言語強制とASR異常出力の相関（4件、全件が同条件）は確認できたが、対象音声の多くが既に削除されており、直接の音声照合による因果立証ができない。この状態でデフォルト挙動（言語強制の可否）をいつ・どう変更するかの判断基準が定まっていない。

- **外部生成コンテンツの検証コスト**: 「改善指示書」のような外部由来の提案を鵜呑みにせず実装で裏取りする規律は、今回2件の誤りを実際に検出できた。有効性は示されたが、この検証にかかる時間コストと、検証を省略した場合のリスクとのトレードオフは定量化されていない。

## 6. 相談質問（NotebookLMへの問い）

1. 複数ロールが同一の作業ディレクトリ・同一のgitチェックアウトを共有し、git worktreeによる物理分離を行っていない設計は、この規模の運用（1セッションで5〜6件の作業が並行的に発生）においてリスクに見合っているか。worktree分離へ移行すべきタイミングの判断基準として何が考えられるか。

2. 統括ロール（采）自身がシェル構文の扱いを誤り、意図しないコマンド実行を引き起こした事故について、透明性をもって即座に報告・是正する事後対応は機能した。同種の事故を未然に防ぐための構造的な対策（エージェントが発信するメッセージ本文のサニタイズ、危険なシェル構文の事前検査など）として、どのようなアプローチが有効か。

3. 外部生成コンテンツ（改善指示書等）を鵜呑みにせず必ず実装で裏取りしてから指示化する現行の規律は、今回2件の誤り検出に成功した。この検証コストと速度のトレードオフをどう最適化すべきか。検証を省略してよい条件はあるか。

4. 言語強制によるASR異常出力という仮説は、複数事例（4件）の相関はあるが、対象データの滅失により直接の因果立証ができない状況にある。このように因果関係の立証が構造的に困難な状況で、デフォルト挙動の変更可否をどのような基準で判断すべきか。

5. エージェント間メッセージング基盤（agmsg）で、実体のない通知が繰り返し発火する現象が原因不明のまま観測された。実害はなかったが、こうした基盤の信頼性をどのように検証・改善していくべきか。

6. 本セッションで扱った作業（バグ修正・改善バックログ・公開設定変更・調査）は、いずれも采の最終承認かユーザーの明示承認を経てから確定させる二重の承認フローを踏んでいる。この慎重さは事故防止に寄与した一方、意思決定の速度とのトレードオフも生じている。この多層承認フローの妥当性・簡略化の余地について、どう評価するか。
