## 2. 背景と目的

tc-ops #440是正（dev tip=574c192で反映済み）後もユーザー実機テストで不具合が再現した。
ユーザー指摘（原文）:
> 「2件目追加したら1件目が消えるような動作をして追いきれない。まずログ詳細追加して」
> 「テストの仕組みちゃんと作って。できたというからテストしたら動作不定で様子がわからない」

**ユーザーが明示した対応順序を厳守する**: ①診断ログ追加 → ②実機再現・原因確定 → ③
（原因確定後、別途）是正方式決定・実装。**本文書は①②のみを対象とする。③は原因確定後、
改めて作業指示書を発行する。**

采が実測したサーバーログの時系列（tc-ops #440コメント記載）:
```
10:27:59 1件目(m6GaYaaJcpU)ダウンロード開始
10:28:14 1件目、blob dataのみでAudio extraction completeログ無し(未完了のまま途切れ)
10:28:16 2件目(qJRxNOAh5sc)ダウンロード開始(1件目blobの2秒後)
10:28:22 2件目が先に文字起こし開始
（以降）1件目はログに一切現れず消失
```

**采の仮説（未確認・saku側の証跡による裏付けが必須。この仮説を前提に実装してはならない）**:
`_enqueue_job()`（`webui.py` L170-192）内のダウンロード処理は `st.spinner()` で包まれているのみで、
実体はメインスクリプト内で同期実行されている（L176-178、`_get_queue().enqueue()` はL192＝関数末尾）。
ダウンロード中に2件目のボタンクリックが発生すると、Streamlitのスクリプト再実行機構が1件目の
実行中スクリプトを `_get_queue().enqueue()` 到達前に中断し、1件目がキュー未登録のまま消える
可能性がある。**これは未検証の仮説であり、ログによる証跡で確定してから是正に着手すること
（推測での修正は禁止、ユーザー明示要望）。**

## 4. 成果物の仕様・要件

### 4-1. 診断ログの追加箇所（全て `item_id` またはenqueue試行を識別するトークン + タイムスタンプ付き）

`core/logging.py` の `get_logger(__name__)` を用いる（既存の統一ロガー方式に準拠、プロジェクト
既存規約）。以下のタイミングでログを出力すること:

1. **enqueue試行開始**: `_enqueue_job()`（`webui.py` L170）の先頭。この時点では`item_id`未採番のため、
   L176で生成する `download_dir` のトークン（`uuid.uuid4().hex[:8]`相当）を仮の識別子として使う
   （生成タイミングをログ出力より前に早める必要があれば、その旨も報告すること）。
2. **`_resolve_input()`開始・完了**（`webui.py` L178呼び出し前後）: ダウンロード所要時間を記録する。
3. **`_get_queue().enqueue()`到達時点**（`webui.py` L192）: 実際にキューへ追加された第間。
   上記1で払い出したトークンとキュー採番後の`item_id`（`core/webui_workflow.py` L106）を
   紐付けてログ出力する。
4. **`dispatch_next()`呼び出し**（`core/webui_workflow.py` L126-142）: 呼び出しの都度、
   `current`（処理中項目の`item_id`、無ければNone）・`queued`件数をログ出力する。
5. **各`QueueItem`の状態遷移**（`mark_done()` L144-149・`mark_failed()` L151-154、および
   `dispatch_next()`内の`PROCESSING`遷移L138-141）: 遷移前後の状態・`item_id`をログ出力する。

**要件**: ログには必ず「①のトークンでダウンロード開始から③のenqueue完了まで一意に追跡できる」
識別子を含めること。ユーザーが「追いきれない」と指摘した状態を解消することが本節の目的。

### 4-2. 実機再現と原因確定

4-1の診断ログを実装した状態で、Streamlit実サーバーを起動し、**1件目投入直後（ダウンロード中、
まだ完了前）に2件目を投入する**操作を実機で再現する（Playwright等、既存の検証手法を踏襲）。
診断ログの実測結果から、1件目が消失する経路を特定する。

### 4-3. テストの仕組み（ユーザー指摘「テストの仕組みちゃんと作って」への対応）

既存の `tests/test_webui_duplicate_url_download.py` 等の単体テストは、Streamlitのスクリプト
再実行による中断シナリオを検証できていない（`_resolve_input()`をモックして関数を直接呼ぶ形の
テストのため、Streamlitのスクリプト実行モデル自体は再現していない）。

**予備調査で検討すること**: 「ダウンロード中の2件目投入によるスクリプト中断」を機械的に
再現・検証できるテスト（単体テストレベルでStreamlitのスクリプト再実行中断を模擬する方法、
または実機Playwright操作を伴う統合テストとして自動化する方法のいずれが妥当か）を設計し、
実装計画に含めて報告すること。**このテストの実装自体は本文書のスコープに含める**
（原因確定のための道具であり、かつユーザーが直接要望した項目のため）。
